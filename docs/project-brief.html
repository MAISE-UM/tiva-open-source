TIVA — Project Brief

Purpose, scope, architecture and request path of the TIVA open-source repository.

Purpose

TIVA is a web application for simulating the plasma (Cp) and effect-site (Ce) concentrations of intravenous anesthetic drugs (propofol, opioids, benzodiazepines, neuromuscular blockers and dexmedetomidine) from a case's dosing history, using published pharmacokinetic (PK) models. A user enters boluses and continuous infusions, or has them loaded from an EHR, and TIVA draws the predicted concentrations over time.

Clinical use disclaimer. TIVA is research and educational software. It is not a cleared or approved medical device, and it has not been validated for clinical decision-making or patient care.

  • Do not use TIVA output to select, dose or titrate any drug for a patient.
  • The simulations are model predictions for a typical patient. Real concentrations vary between patients and can differ greatly from the model.
  • Results depend on the accuracy of the data entered or imported (doses, times, age, weight, height, sex). Check them.
  • Anyone who uses or deploys TIVA is responsible for validating it for their purpose and for complying with the regulations that apply to them.
  • The software is provided “as is”, without warranty of any kind.

Architecture

Solid lines: request path. Dashed line: browser-side EHR redirects handled directly by the API.

Request path

  1. The browser requests a page from the Next.js server. client/proxy.ts runs first: it checks the refresh/access tokens, redirects unauthenticated users to /auth/logout, loads the user's permissions from the API (Admin/GetUserPermissions), stores the route-relevant ones in the user-permissions cookie, and redirects to /404 if the route is not allowed.
  2. Client components call server actions in client/api/*.tsx ('use server'). They go through fetch_api_wrapper (api-wrapper.tsx), which reads the X-Access-Token cookie on the Next.js server, adds it as a bearer token, calls the API at NEXT_PUBLIC_API_BASE_URL, and, if the API answers with an expired token, calls Auth/RefreshTokenUser with the X-Refresh-Token cookie and retries once.
  3. Most data calls are GET|POST /Api/{schema}/{endpoint}. The API looks the endpoint up in its in-memory EndpointCache (loaded from api.Endpoints, api.EndpointParameters and api.EndpointSecurity), checks that one of the user's roles has access, and either runs a stored procedure or calls a REST URL.
  4. The response is always the ReturnInfo envelope: { bSuccess, sErrorInfo, oReturnObject }.
  5. Drug parameters are not in the client source. Meds/GetDrugModels runs core.GetMedicationModels, which executes each model's model.PK_* procedure for the patient's weight, age, height and sex. The client then runs the simulation in the browser (simulation-algorithm.html).

Main features

  • Dashboard (/): patient covariates, dose tables per drug (bolus, start infusion, dose change, stop infusion), one Plotly graph per drug (expandable to a full-size view), graph options, optional per-graph JSON data export (permission ExportGraphToFileButton).
  • EHR mode (/?fromEhr=true): loads weight, height, case times and drug administrations over SMART on FHIR and refreshes them every 5 minutes. See ehr-launch-flow.html.
  • MPOG case search: optional, MPOG members only (database-defined endpoint, disabled by default).
  • Reports (/reports): internal login report from admin.GetUsersLoginCount and an optional embedded external report.
  • Administration: user admin (/admin/user-admin) and an in-app API editor (/admin/api-edit) that edits endpoint definitions in the database, then reloads the cache.
  • Disclaimer and reCAPTCHA gate (/disclaimercaptcha) with a per-host skip list.
  • Logging: graph inputs (api.Graph_Logs), user activity, client errors and logins to SQL Server; optional SMTP error mail.

Security notes

  • Never run a server with Environment set to Development. In that mode test accounts sign in without a password and /Admin/RestoreSession and /Admin/GetSession are enabled.
  • Config files with secrets (appsettings.json, web.config, .env, keys/) are gitignored. Keep them out of source control.
  • The API keeps sessions, OAuth state and the endpoint cache in memory, so it must run as a single instance.
  • api.UserLogin_Log can hold patient ID, MRN and name from the EHR launch. Treat the database as holding protected health information.
  • Report vulnerabilities as described in SECURITY.md.
