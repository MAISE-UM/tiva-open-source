TIVA — EHR Setup Guide

How to connect TIVA to an EHR with SMART on FHIR (tested with Epic): how the pieces fit together, how to configure the login, and how to configure the patient data the dashboard loads.

1. How the pieces fit 2. Before you start 3. What happens during a login 4. Register with the EHR 5. Create the key pair 6. Configure the login 7. How patient data is loaded 8. Configure the patient data 9. Test it 10. Troubleshooting 11. Where things are defined

This page is a setup walkthrough. For a step-by-step trace of one launch through the code, with a sequence diagram, see ehr-launch-flow.html. For the endpoint engine and the full list of seeded endpoints, see api.html § Endpoint engine.

All site-specific values live in the Ehr section of the API settings. You should not need to change code to connect TIVA to your EHR.

1. How the pieces fit together

Login travels as redirects through the browser. Patient data is fetched by the API directly from the EHR, using the user’s EHR token held in the API’s memory.

There are two separate jobs, and they are configured in different places:

JobWhat happensDefined inChanging it needs
LoginThe EHR sends the user to TIVA, the user is authenticated with the EHR, and TIVA signs them in.Code plus the Ehr settings (EhrOAuthController, SmartOnFhirService)Editing settings, then recycling the API
Patient dataThe dashboard asks the API for the patient’s data; the API calls the EHR with the user’s EHR token.Database rows (api.Endpoints and related tables)Editing rows, then POST /Admin/ReloadEndpoints

Two terms are used throughout and are easy to mix up:

  • A route is a URL the TIVA API itself answers, for example ehr/launch. The login routes are mapped when the API starts, with paths taken from Ehr:Routes.
  • An endpoint is a database-defined API call, for example FHIR/GetVitalSigns. All endpoints are served by one generic route, /Api/{schema}/{endpoint}. For REST endpoints, each row tells the API which EHR URL to call and how.

2. Before you start

You need:

  • The TIVA API and client deployed and working without the EHR (see api/README.md and client/README.md). The database must be built (examples/CreateDB.sql) and seeded (examples/SeedData.sql).
  • A public HTTPS host name for TIVA, for example tiva.example.org. The EHR redirects the user’s browser to it, and the login cookies are set Secure with SameSite=None, so plain HTTP does not work.
  • A SMART on FHIR app registration with your EHR vendor (section 4). For Epic this is normally done by your hospital’s Epic team. Allow time for it: you cannot test the login until it exists.
  • Access to the EHR’s non-production environment and a test patient with a surgical case.
  • OpenSSL (or another way to create an RSA key pair), for section 5.

About /REST. On a standard Windows deployment, IIS serves the API as an application with the alias REST. IIS removes that prefix before the API sees the request, so inside the API the route is ehr/launch, while the EHR and the browser use /REST/ehr/launch. Everything on this page written as /REST/... is the outside URL. If you host the API a different way, adjust the prefix.

Where the settings go

On a server, the Ehr settings go in the IIS web.config as MA_* variables. On your own machine they go in appsettings.json. A setting’s JSON path becomes its variable name: Ehr → ClientId is MA_Ehr__ClientId, and list items get an index (MA_Ehr__AllowedIssuers__0). If a value is in both places, the web.config wins. Details are in api/README.md, section “Which config file do I edit?”. Templates: api/deploy/appsettings.example.json and api/deploy/web.config.example.

3. What happens during a login

Read this once so the settings in the next sections make sense. ehr-launch-flow.html has the sequence diagram and a code-level trace.

  1. Launch. A user clicks the TIVA link on a case in the EHR. The EHR opens /REST/ehr/launch and adds query parameters: iss (the EHR’s FHIR server URL), launch (a one-time token), and the case ID and the user’s name under the parameter names you set in Ehr:LaunchParameters.
  2. Authorize. TIVA checks that iss is one it trusts (Ehr:AllowedIssuers), downloads the EHR’s FHIR metadata (the CapabilityStatement) to find the EHR’s authorize and token URLs, remembers the case details under a random state value, and redirects the browser to the EHR’s authorize page.
  3. Callback. The EHR sends the browser to Ehr:RedirectUrl (/REST/ehr/callback) with a one-time authorization code. TIVA keeps the code in a cookie and sends the browser to the client page auth/ehrloading.
  4. Complete. That page sends the browser to /REST/ehr/complete. Now TIVA, server to server:
    1. exchanges the code for tokens at the EHR’s token URL, proving who it is with a client assertion: a short-lived JWT signed with TIVA’s private key (section 5);
    2. checks the id_token signature using the EHR’s public keys (Ehr:JwksUrl), and its issuer and audience (Ehr:Issuer, Ehr:ClientId);
    3. turns a claim in the id_token into a TIVA user name and finds that user, or creates one (Ehr:User);
    4. creates TIVA’s own login tokens, and stores them together with the EHR’s access and refresh tokens in a server-side session. The browser gets only TIVA’s cookies.
  5. Dashboard. TIVA redirects to auth/ehrlaunch, which opens the dashboard with ?fromEhr=true and starts the patient data load (section 7).

If anything fails in step 4, the user is redirected to Ehr:ClientRoutes:Failure (default: the Search page) and the reason is written to the error log.

Timing limits. The state is remembered for 10 minutes, so the user must finish the login within that time or the case ID is lost. The EHR metadata is cached in memory (60 minutes, renewed each time it is used), so after changing MetadataUrl or MetadataHeaders recycle the API.

For Epic, create a SMART on FHIR app (for example through the Epic on FHIR developer site, or ask your Epic team to create it) and give them:

5. Create the client assertion key pair

To get tokens, TIVA must prove to the EHR that it is the registered app. It does this by signing a small JWT with a private key; the EHR checks the signature with the matching public key, which it downloads from the JWK Set URL you registered.

openssl genrsa -out ehr-private.pem 2048
openssl req -new -x509 -key ehr-private.pem -out ehr-public.pem -subj "/CN=tiva" -days 3650
  • Put the contents of ehr-private.pem in Ehr:ClientAssertion:PrivateKey. Never commit it.
  • Put the contents of ehr-public.pem (an X.509 certificate) in Ehr:ClientAssertion:PublicCertificate. TIVA publishes it at /.well-known/jwks.json for the EHR to fetch.
  • In JSON, write PEM line breaks as \n. In web.config the value can contain real line breaks.

The assertion TIVA builds has these claims: iss and sub = your ClientId, aud = the token URL, a random jti, and exp = now + LifetimeMinutes (default 2). It is signed with Algorithm (default RS384). If the EHR identifies keys by kid, Kid must match what the EHR has on file; set IncludeKidHeader to false if the EHR does not want it. Epic’s guide: Creating a key pair with OpenSSL.

6. Configure the login

A minimal working configuration

This is the smallest Ehr section for an Epic-style EHR. Anything you leave out takes the default from Models/EhrSettings.cs. The full example with every setting is api/deploy/appsettings.example.json.

"Ehr": {
  "Enabled": true,
  "DisplayName": "EHR",
  "ClientId": "<client ID from the app registration>",

  "Issuer": "https://ehr.example.org/oauth2",
  "JwksUrl": "https://ehr.example.org/oauth2/jwks",
  "MetadataUrl": "https://ehr.example.org/api/FHIR/R4/metadata",
  "AllowedIssuers": [ "https://ehr.example.org/api/FHIR/R4" ],

  "RedirectUrl": "https://tiva.example.org/REST/ehr/callback",

  "MetadataHeaders": { "Epic-Client-ID": "{ClientId}" },

  "ClientAssertion": {
    "PrivateKey": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----",
    "PublicCertificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
    "Kid": "ehr"
  }
}

Of these, AllowedIssuers is the one you can leave out at first (see its row below). The rest is what an Epic-style EHR typically needs (MetadataHeaders is Epic-specific, and DisplayName only changes labels).

Also make sure the settings in the URL table are correct: JwtAuthentication:ValidIssuer (with trailing /), AppSettings:COOKIE_DOMAIN, AppSettings:SITE_URL and AppSettings:AUTH_JKU_URL, and the client’s NEXT_PUBLIC_EXTERNAL_API_BASE_URL.

Finding the value. An accepted launch does not log the iss (only the names of the query parameters), so with an empty list it will not be in the log. Ways to get it:
  • Take Ehr:MetadataUrl without the trailing /metadata. The launch downloads {iss}/metadata, so for the same server the two line up (for example .../api/FHIR/R4/metadata → .../api/FHIR/R4).
  • Read the iss query parameter of the first request to /REST/ehr/launch: in the IIS request log, which records query strings, or in the browser’s developer tools (Network tab, with “Preserve log” on) during a test launch.
  • Set the list to a placeholder value for one test launch. The launch is then rejected with 403 and the error log shows EHR launch rejected, issuer not allowed: <iss>.

Mapping the EHR user to a TIVA user

After the id_token is validated, TIVA needs a TIVA user name. Ehr:User (EHR launch) and Ehr:StandaloneUser (standalone launch) control how:

SettingDefault (User)Meaning
ClaimTypepreferred_usernameWhich claim of the id_token holds the user name.
StripPrefixes[]If the value starts with one of these (ignoring case), the prefix is removed. Only the first match is used.
LowercasefalseConvert the result to lower case.
FallbackSuffixes[]Tried in order if the plain name is not found.
AutoCreatetrueCreate the TIVA user if no match is found.

StandaloneUser has the same settings, but defaults to Lowercase: true and AutoCreate: false.

Worked example

The EHR returns preferred_username = "HOSPITAL\JSmith", and your TIVA users are stored as jsmith@hospital.org:

"User": {
  "ClaimType": "preferred_username",
  "StripPrefixes": [ "HOSPITAL\\" ],
  "Lowercase": true,
  "FallbackSuffixes": [ "@hospital.org" ],
  "AutoCreate": true,
  "DefaultRoleId": "2"
}
  1. Take the claim: HOSPITAL\JSmith.
  2. Strip the prefix: JSmith. Lower-case it: jsmith.
  3. Look for a TIVA user named jsmith. If found, sign in as that user.
  4. If not found, try jsmith@hospital.org. If found, sign in as that user.
  5. If still not found and AutoCreate is true, create a user named jsmith with role 2, using the first and last name from the launch parameters.
  6. If AutoCreate is false, the login fails and the user is sent to the Failure page.

The backslash is doubled in JSON ("HOSPITAL\\"). In web.config write it once: <environmentVariable name="MA_Ehr__User__StripPrefixes__0" value="HOSPITAL\" />.

The user name matters beyond login. Every call TIVA makes to the EHR for that user includes it, and the endpoint security checks the user’s role (section 8), so a created user must have a role that is allowed to call the FHIR endpoints.

What the client reads

GET /REST/ehr/client-config returns Enabled, DisplayName, the Complete path and DataMapping (section 8). It contains no secrets. The client calls it to know where to send the browser after auth/ehrloading, so it must work for the login to complete.

7. How patient data is loaded

After login the dashboard opens as /?fromEhr=true. The client function searchFHIR() (client/lib/med-helpers.tsx) then makes up to four calls through the API, in order, and stops at the first one that fails or comes back incomplete, leaving whatever it has loaded so far:

#Client functionAPI endpointMethodWhat it fetchesStops the load if
1getFHIRVitalSignsFHIR/GetVitalSignsGETWeight and height (FHIR Observation)No weight or no height is found
2getEhrSurgicalCaseFHIR/GetSurgicalCasePOSTPatient name, sex, date of birth, MRN; procedure; operating room; anesthesia start and stop timesThe case has no patient date of birth, name, procedure or room
3getFHIRMedicationStatementsFHIR/GetMedicationStatementsGETThe patient’s medication orders from 3 days before anesthesia startNo order matches a TIVA drug
4getMedicationAdministrationsFHIR/GetMedicationAdministrationPOSTThe doses given for the matched orders(end)

Where the inputs come from:

  • The case ID and patient ID were stored at login in the X-SurgicalID cookie as <case id>||<patient id>. Step 1 uses the patient ID, step 2 the case ID.
  • Step 4 uses the MRN and visit contact number from step 2, and the order IDs from step 3.
  • Orders are matched to TIVA drugs by name using each drug’s Medication_Search_Terms (every term must appear in the name, and a term starting with ! must not). See client.html § Dashboard.
  • The dashboard repeats the whole load every 5 minutes so new doses appear during the case.

The client does not call the EHR itself. It calls TIVA’s generic API, for example GET /REST/Api/FHIR/GetVitalSigns?patient=....

What the API does with one call

Take FHIR/GetVitalSigns:

  1. The generic handler (ApiController) looks up FHIR/GetVitalSigns in the endpoint cache and checks that the caller’s role is allowed.
  2. The endpoint’s Credential_Source is UserSession, so the API first refreshes the EHR token if it is older than Ehr:TokenRefreshMinutes. If the user has no session (the API was restarted, or the session expired), the call fails with Authentication Token Invalid.
  3. It reads the property named by Credential_Key (FhirAccessToken) from the user’s server-side session and uses it as the bearer token.
  4. It builds the URL: the URL base named by URL_Base (here EhrFHIR, looked up in admin.Application_Lists) + the endpoint’s URL: 
    https://ehr.example.org/Interconnect/  +  api/FHIR/R4/Observation
  5. It adds the parameters defined for the endpoint (api.EndpointParameters). Here the client sends patient; the others are fixed by the row: 
    ?patient=<id>&category=vital-signs&code=11,14
  6. It sends the request with Authorization: Bearer <EHR access token> and returns the EHR’s response to the client.

The browser never receives the EHR tokens.

8. Configure the patient data

8.1 Set the EHR base URL

All FHIR endpoints share one URL base. Each endpoint row’s URL_Base column holds a name, not a URL, and the real address is the List_Value of the admin.Application_Lists row with that name (Category = 'APIEditor', Section = 'URLBases', List_Key = the name). In the seed data the name is EhrFHIR and the value is a placeholder:

UPDATE admin.Application_Lists
SET    List_Value = 'https://ehr.example.org/Interconnect/'
WHERE  Category = 'APIEditor' AND Section = 'URLBases' AND List_Key = 'EhrFHIR';

The name is only a label. Your database may use a different one (for example MyHospitalFHIR). Use the name your endpoints use:

SELECT DISTINCT URL_Base FROM api.Endpoints WHERE Endpoint_Name LIKE 'FHIR/%';

Each name returned needs a matching List_Key row. If one is missing, calls fail with URL Base Not Found.

Keep the trailing / on the value: the endpoint URLs are appended directly, with no separator added.

The URL base is cached in memory for up to 60 minutes (sliding), and ReloadEndpoints does not clear it. After changing it, recycle the API (restart the IIS app pool).

8.2 Fill in the Epic web-service URLs

Four of the seeded endpoints call standard FHIR and already have a URL. The other three call Epic’s proprietary web services (not standard FHIR) and are seeded with the placeholder REPLACE_WITH_EPIC_API_PATH:

EndpointEpic API it callsUsed by the dashboard
FHIR/GetSurgicalCaseGetSurgicalRecord (Specialty, Surgery)Yes (step 2)
FHIR/GetMedicationAdministrationGetMedicationAdministrationHistory (Clinical, Patient)Yes (step 4)
FHIR/GetFlowSheetRowGetFlowsheetRows (Clinical, Patient)No. Seeded but not called by the dashboard.

Find each API’s path in your Epic documentation (open.epic.com or your site’s Interconnect API list), using the version your Epic supports. The path is relative to the URL base from 8.1:

UPDATE api.Endpoints
SET    URL = '<path from your Epic documentation>'
WHERE  Endpoint_Name = 'FHIR/GetSurgicalCase';

The standard FHIR endpoints are FHIR/GetVitalSigns (api/FHIR/R4/Observation) and FHIR/GetMedicationStatements (api/FHIR/STU3/MedicationStatement). Also seeded: FHIR/GetMedication and FHIR/GetMedicationRequest. The dashboard does not call those two. Change any of the paths if your EHR uses different ones.

A different EHR. Only Epic is supported out of the box. The two required web-service endpoints, a surgical case record and medication administrations, return Epic-shaped JSON that the client parses in searchFHIR(). An EHR with different services needs equivalent endpoints and, if the response shape differs, changes to that client code.

8.3 Check the endpoint parameters

Each endpoint’s request is defined by rows in api.EndpointParameters. For each parameter the row says:

  • Where it goes: Parameter (query string), Body (JSON body of a POST), or URL (appended to the path).
  • Who supplies it: either the client (it must send it, or the call fails with Missing Required Parameters), or the system (a fixed value stored on the row).
  • A template with {var} as the value. For example gt{var} turns 2026-01-01 into gt2026-01-01, and {"ID":"{var}","Type":"Internal"} builds an object for APIs that want IDs as objects.
  • For lists, a delimiter (|): OrderIDs is sent as a|b|c and expanded to a list of objects.
  • A flag that fills the parameter with the signed-in user’s TIVA user name. The Epic UserID parameters use it, and the companion UserIDType parameter is a fixed value, systemlogin.

The seeded rows were exported from a working Epic setup. Compare them with the request body in your Epic documentation and edit any that differ (the comment above each placeholder row in SeedData.sql says the same). The client sends these names, so keep them: patient and effective (statements), SurgicalRecordID (case), and PatientID, ContactID and OrderIDs (administrations).

The data model and the editing endpoints are described in api.html § Endpoint engine. api/TIVA_API/examples/ExportEhrEndpoints.sql exports all the FHIR rows from a working database, to copy to another site.

8.4 Check who can call the endpoints

Access is controlled by api.EndpointSecurity. The seed grants the FHIR endpoints to the Administrator (1) and User (2) roles. Users created by the EHR login get Ehr:User:DefaultRoleId (default 2), so they can call them. If you change the default role, check that it is still allowed.

8.5 Reload the endpoints

After editing endpoint rows (URLs, parameters, security), call POST /REST/Admin/ReloadEndpoints as an administrator, or recycle the API. This reloads api.Endpoints, EndpointParameters and EndpointSecurity into memory.

8.6 Map your EHR’s labels (Ehr:DataMapping)

The client finds the values it needs by matching text in the EHR’s responses. The defaults are for Epic’s naming; your EHR may use different names.

SettingDefaultWhat the client looks for
WeightLabelWeightThe vital-signs Observation whose code.text is this. Unit kg is kept as kg; any other unit is treated as lb.
HeightLabelHeightThe same, for height. Unit cm is kept as cm; any other unit is treated as inches.
AnesthesiaStartEventAnesthesia StartThe surgical-case timing event whose Title is this. Its StartDateTime becomes the anesthesia start.
AnesthesiaStopEventAnesthesia StopThe same, for the end. If there is none, the case’s discharge time is used instead.
ProcedurePafIndex1Which entry of the case’s PAFValues list holds the procedure name.

To find the right values for your site, make one call from a test launch (section 9) and read the response in the browser’s network tab: look at the code.text of the Observations and the Title of the timing events. If anesthesia start is not found, the dashboard shows “Anesthesia Start is not detected. Please relaunch from the EHR”.

These settings are in the API’s Ehr section, but they are read by the client: it fetches them from GET /REST/ehr/client-config and keeps them until the page is reloaded.

9. Test it

Work through these in order. Each step tests the one before it.

  1. API is up. GET /REST/Admin/Health returns Healthy.
  2. Settings are loaded. GET /REST/ehr/client-config returns Enabled: true and your DisplayName and DataMapping. This route exists even when the EHR is disabled, so check the values. If you get Enabled: false, or the default DisplayName of EHR when you set another, the Ehr section is not being read: check which config file the server uses (section 2).
  3. Keys are published. GET /REST/.well-known/jwks.json lists two keys: your EHR key with the kid you set in Ehr:ClientAssertion:Kid, and the API token key. If the EHR key is missing, Ehr:ClientAssertion:PublicCertificate is empty.
  4. Launch. Open a test patient’s case in the EHR’s non-production environment and click the TIVA link. Watch the browser’s address bar: you should pass through the EHR, then /REST/ehr/callback, auth/ehrloading and /REST/ehr/complete, and end on the dashboard.
  5. Login result. A successful login appears in api.UserLogin_Log (with the source set to your DisplayName). A failure sends you to the Failure page; the reason is in the error log (written by api.SaveErrorLog).
  6. Data. Open the browser’s developer tools, Network tab, and look at the calls to /REST/Api/FHIR/... after the dashboard opens. Each response has bSuccess, sErrorInfo and oReturnObject. Check them in order: vital signs, then surgical case, medication statements and administrations. The dashboard fills in as each one succeeds.
  7. Token refresh. Keep the dashboard open for longer than TokenRefreshMinutes. The next 5-minute reload should still work, which shows the token refresh does.

For development only, with Environment set to Development (never in production), GET /REST/Admin/RestoreSession?username=<user> restores the cookies of a user whose session is cached, so you can reopen the dashboard without launching from the EHR again.

10. Troubleshooting

Login

What you seeLikely cause
/ehr/launch returns 404Ehr:Enabled is not true, or the path differs from Ehr:Routes.
HTTP 403 “Launch issuer not allowed”The launch iss is not in Ehr:AllowedIssuers. The exact value is in the error log.
500 “Internal Auth Security Error:” at launchThe metadata could not be downloaded, or no authorize URL was found in it. Check {iss}/metadata, MetadataHeaders, and EndpointDiscovery (try ByIndex).
The EHR shows an error before returning to TIVAThe registration does not match: RedirectUrl, ClientId, scopes or launch URL. The error is shown by the EHR.
500 “Failed to pull identifier” at ehr/completeThe code cookie did not arrive. Check HTTPS, that AppSettings:COOKIE_DOMAIN matches the host, and that the browser is not blocking cookies. Opening ehr/complete directly, without going through the callback, also causes this.
500 “Internal Auth Error:” at ehr/completeThe token exchange failed; the log has “EHR token exchange failed” and the status. Common causes: the EHR does not accept the client assertion (wrong key pair, Kid or Algorithm, or the JWK Set URL is not reachable by the EHR), the RedirectUrl differs from the one used at launch, or the code was already used or has expired.
Redirected to the Failure page; log says “EHR Authentication failed”The id_token failed validation: Issuer or ClientId does not match, or JwksUrl is wrong.
Redirected to the Failure page; log says “User not found”The claim named by ClaimType is missing, or no user matches and AutoCreate is false. Decode the id_token to see what the EHR sends.
Logged in, but no patient data (log line “EHR launch state not found or expired”)More than 10 minutes passed between launch and completion, or the API was restarted in between. Relaunch.
Logged out after a whileSessions live in memory and expire after 60 minutes without use. Restarting or recycling the API ends all sessions. EHR users relaunch from the EHR.

Patient data

What you seeLikely cause
Authentication Token InvalidThe user’s session is gone (the API was restarted) or the user did not log in through the EHR. Relaunch from the EHR.
Failed to refresh FHIR token. Session may be invalid.The EHR rejected the refresh. Check the log line “FHIR token refresh failed” for the status. Ehr:MetadataUrl must be set, because the refresh needs it.
URL Base Not FoundThere is no admin.Application_Lists row (APIEditor / URLBases) whose List_Key matches the endpoint’s URL_Base name (see 8.1).
Missing Required Parameters: ...The client did not send a parameter the endpoint requires. Compare the endpoint’s parameter rows with the client function.
The call succeeds but the response is an EHR error messageThe API only treats “no response at all” as a failure. An HTTP 401, 403 or 404 from the EHR is returned as the response body with bSuccess true. Read oReturnObject. Typical causes are a wrong URL or base URL, a missing scope or API access on the registration, or wrong parameters.
Changes to the URL base have no effectThe URL base is cached. Recycle the API.
Changes to endpoint rows have no effectCall POST /Admin/ReloadEndpoints.
The dashboard stays empty after loginThe load stops at the first incomplete step (section 7). Check the Network tab to find which call returned nothing. Usually a DataMapping label does not match, so weight or height is not found.
“Anesthesia Start is not detected”AnesthesiaStartEvent does not match a timing event Title, or the event has not been documented yet.
Some drugs are missingThe drug’s Medication_Search_Terms do not match the order name in the EHR, or the infusion is not yet validated in the EHR.

Hosting notes

  • The API keeps sessions (including EHR tokens), OAuth state, the URL base and the endpoint cache in memory. Run it as a single instance: one server and one IIS worker process. Restarting or recycling the API signs EHR users out, and they relaunch from the EHR.
  • The login log (api.UserLogin_Log) stores patient identifiers from the launch. Treat the database as holding protected health information.
