Sign-in paths

PathRouteHow it works
Username and password (LDAP)POST /Auth/AuthenticateUserThe user must already exist in admin.Application_Users (admin.GetUserDetails returns roles and Test_Account). The password is checked by an LDAP bind: Ldap:Host, Port, UseSsl, and BindDnTemplate formatted with the username and BaseDn. LDAP must be enabled (Ldap:Enabled), otherwise login fails with “LDAP login is not enabled”. On success the API issues tokens and sets the cookies. Logins are recorded in api.UserLogin_Log with source LDAP.
EHR (SMART on FHIR)GET /REST/ehr/launch … ehr/completeThe EHR proves who the user is with an id_token; TIVA maps it to a TIVA user and optionally creates the user. See ehr-launch-flow.html.
EHR standaloneGET /REST/ehr/standaloneSame, without a patient context.
Swagger / scriptsPOST /Auth/AuthenticateUserAPISame LDAP check, but returns the tokens in the response body instead of cookies. Intended for the Swagger UI.
Machine clientPOST /Auth/AuthenticateClientClient ID and secret (see API clients).

There is no self-registration: an administrator adds users in the Admin UI (admin.AddUser) and gives them roles, unless EHR auto-create is enabled for the EHR path. The first administrator is created with admin.AddUser after loading the seed data.

Tokens and cookies

ItemDetails
Access tokenJWT signed RS384 with JwtAuthentication:JWT_PRIVATE_KEY. Lifetime 120 minutes (TokenService.ExpiryDurationMinutes). Claims: name (username), nameidentifier (random GUID), givenname (Last, First), authenticationmethod (USER or CLIENT) and one role claim per role. Header carries kid (JwtAuthentication:Kid, default tiva-api-auth) and jku (AppSettings:AUTH_JKU_URL).
Refresh tokenSame format and key, lifetime 480 minutes (8 hours).
ValidationThe API validates issuer and audience (JwtAuthentication:ValidIssuer, ValidAudience) and the signature with the public half of the key. The bearer handler is configured with ValidateLifetime = false; the dynamic Api/* controller checks the exp claim itself and answers 401 when it has passed. The Next.js server verifies tokens against /.well-known/jwks.json (jose, RS384).
CookiesX-Access-Token and X-Refresh-Token: HttpOnly. X-Username: readable. All with Secure, SameSite=None, Path=/ and domain AppSettings:COOKIE_DOMAIN. The API reads the access token from the X-Access-Token cookie (OnMessageReceived) and also accepts a bearer header.
Session cacheOn login the API stores a Session per lower-cased username in its in-memory distributed cache: TIVA tokens and, for EHR logins, the EHR id/access/refresh tokens and token time. REST endpoints with Credential_Source = UserSession read the EHR token from it.
LogoutPOST /Auth/LogOut expires the three cookies. The client's logout() also deletes disclaimer_agreement and user-permissions.

Refresh

  1. A server action sends a request with the access token. The API answers 401 when the token is expired.
  2. fetch_api_wrapper (client.html) POSTs to /Auth/RefreshTokenUser with the refresh token as bearer token.
  3. The API validates it, reloads the user and roles from the database, issues a new access/refresh pair, updates the session cache and sets new cookies. 401 means the refresh token is no longer valid and the user must sign in again (proxy.ts redirects to /auth/logout).

/Auth/RefreshTokenClient does the same for machine clients. api/TIVA_API/examples/exampleJSWebCallerThatCanRefreshToken.js is a sample caller.

Endpoint security (API)

Authorization for dynamic endpoints is data, not code:

admin.Application_Users ─┐
                         ├─ admin.Application_User_Roles ─┐
admin.Application_Clients ┘ (…_Client_Roles)              ├─ admin.Application_Roles ─ role name = JWT "role" claim
                                                           │
api.Endpoints ─ api.EndpointSecurity (Endpoint_ID, Role_ID, Has_Access) ┘
  • When the endpoint cache loads (api.GetEndpoints), each endpoint gets a set of role names with access (RolesWithAccess).
  • For a call to /Api/{schema}/{endpoint} the controller looks the endpoint up by name. It is allowed when Allow_Anonymous is set, or when any role claim in the token is in RolesWithAccess. If the endpoint exists but no role matches, the API returns 403. An unknown endpoint name returns bSuccess = false with “This Endpoint Either Does Not Exist Or User Does Not Have Access”.
  • Every controller also has a default policy that requires an authenticated user unless the action is marked [AllowAnonymous] (see api.html).
  • Seeded roles: Administrator (1), User (2) and MPOGGlobal (3).

Endpoint definitions are edited with the in-app API editor (/admin/api-edit) or by SQL, followed by POST /Admin/ReloadEndpoints (or an app pool recycle) because the cache is only loaded at start-up.

UI permissions (client)

What a user sees is also data. admin.GetUserPermissions returns the functions the user's roles (plus every Default_Allow function) may use, joined to the routes they belong to.

TableRole
admin.Application_FunctionsEvery UI element: Type is Route, Category, DropdownLink, DropdownItem or Button. Function_Details holds the path (for routes and links) or a switch name. Parent_ID nests items under a category (for example the user dropdown). Default_Allow makes it available to everyone.
admin.Application_Role_FunctionsWhich roles get which functions.
admin.Application_Routes, Application_Route_FunctionsWhich page (Shared, Dashboard, Reports, User-Admin, API-Edit, …) each function appears on. Shared functions apply everywhere.

In the client, proxy.ts uses the result to decide whether a path is allowed and writes the route-relevant subset to the user-permissions cookie; components such as the header's user dropdown and the graph's “Export to File” button check that list (for example permission.Function_Name === 'ExportGraphToFileButton'). Details: client.html § proxy.ts.

The client-side check only hides UI. Data access is enforced by the API (endpoint security above), so permissions for routes and for endpoints must both be set up for a feature to work.

API clients (machine to machine)

Clients are rows in admin.Application_Clients with roles in admin.Application_Client_Roles. They can only be created with the admin.AddClient endpoint, because the secret must be encrypted before it is stored (AES with AppSettings:SECRET_KEY; see CipherService and POST /Admin/EncryptString). A client signs in with POST /Auth/AuthenticateClient (client ID and secret) and receives tokens whose authenticationmethod is CLIENT. Values in admin.Application_Configurations are expected to be stored encrypted the same way.

Development mode (never in production)

When Environment is Development the repository accepts users marked Test_Account without any password, through the normal login and the EHR login routes, and GET /Admin/RestoreSession and GET /Admin/GetSession are enabled (they return or restore any user's session by name). With any other value, a test account cannot sign in at all. Never set Environment=Development on a reachable server or one with real data, and keep ASPNETCORE_ENVIRONMENT=Production so Swagger and the developer exception page stay off. See api/README.md and SECURITY.md.
