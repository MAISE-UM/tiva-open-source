TIVA — Client Reference

Developer reference for the Next.js client in client/: routes, request handling, server actions, components, simulation code, configuration and tests.

Overview

Package tiva-client (GPL-3.0-or-later). Next.js 16 with the App Router and Turbopack in development, React 19, TypeScript 5, Tailwind CSS 3 with tailwindcss-animate, Radix UI primitives wrapped in components/ui/* (shadcn style, see components.json), Plotly via plotly.js-dist-min. Path alias @/* maps to the client root.

Server actions accept request bodies up to 3 MB (next.config.ts, serverActions.bodySizeLimit), which matters because graph logs post the full dose tables.

proxy.ts (route guard)

Next.js 16 runs proxy.ts before each request that matches /((?!api|_next/static|_next/image|favicon.ico).*). It does the following:

  1. Skip list. Paths containing auth, 404, images or admin/health are let through.
  2. Authentication. refreshTokenInit() checks the X-Refresh-Token cookie and verifies it against the API's JWKS (RS384, jose). Missing or invalid means a redirect to {NEXT_PUBLIC_LAUNCH_BASE_URL}/auth/logout.
  3. Permissions. It reads the username from the refresh token, then calls getUserPermissions(username) (GET API/Admin/GetUserPermissions/{user}), which returns rows of type Route and non-route rows (buttons, dropdowns and so on).
  4. Per-route cookie. For a path such as /admin/api-edit it builds the chain Shared, admin, api-edit and keeps the permission rows whose Route matches, so common items are defined once under the Shared route. The result is written to the readable user-permissions cookie. / is treated as /Dashboard.
  5. Route check. If no Route row has a Function_Details equal to the requested path, the user is redirected to /404.

On the browser side, PermissionProvider (app/contexts/PermissionContext.tsx) verifies the access token (jwtPayload()) and reads the cookie on every path change; usePermissions() exposes { userPayload, permissions }. LayoutProvider and useLayoutToggle(header, footer) let a page hide the shared header or footer.

API layer (server actions)

All files in client/api/ are 'use server' modules. Components import them like normal functions; they run on the Next.js server.

api-wrapper.tsx

  • fetch_api_wrapper(type, path, parameters, body, needsAuth, cacheType, includeCredentials): builds {NEXT_PUBLIC_API_BASE_URL}/{path}, adds query parameters, sends the body for POST, and adds Authorization: Bearer <X-Access-Token> when needsAuth is true.
  • Any 401 response is turned into TokenExpired. The wrapper then POSTs to Auth/RefreshTokenUser with the X-Refresh-Token as the bearer token, copies the Set-Cookie headers into the Next.js cookie store, reads the new access token and retries the original request once. 401/403 from the refresh call throws UnableToRefreshToken. Other non-2xx responses throw RequestFailed. The wrapper returns { data } on success or { error } on failure.
  • axios_post_api_wrapper: a multipart FormData POST variant with the same refresh handling.

Response envelope. The API returns { bSuccess, sErrorInfo, oReturnObject } where oReturnObject is a JSON-encoded string. processResponse<T>(raw) (lib/utils.ts) parses it into DataResponse<T>. processUserResponse additionally splits the Roles string (pipe separated) into role options.

Dashboard

components/dashboard/Dashboard.tsx owns the page state: patient covariates, reference time, maxTime (minutes of projection), the medication list, drug models, per-drug dose tables (medTables) and the computed simulation per drug (tciMap).

Load sequence

  1. On mount, jwtPayload() verifies the access token. Unless the host is in NEXT_PUBLIC_CAPTCHA_DISABLED_HOSTS, a user who has not agreed to the disclaimer or solved the captcha is sent to /disclaimercaptcha.
  2. load() → loadMeds() calls getMedications(). Each medication's comma-separated Units is split into infusion units (contain min or hr) and bolus units. Medications with Load_Graph_Default are graphed by default.
  3. In EHR mode searchFHIR() (lib/med-helpers.tsx) reads the X-SurgicalID cookie, then calls vital signs (weight, height), GetSurgicalCase (patient, procedure, room, anesthesia start/stop) and medication orders/administrations. Labels come from ehr/client-config DataMapping. The result fills covariates and referenceTime.
  4. refreshDrugModels() calls Meds/GetDrugModels with age (years), height (cm), weight (kg) and sex. The database computes each model's Vc, k10, k12, k21, k13, k31, ke0 (and k01) for that patient.
  5. DoseSection turns administrations into dose-table rows (createDoseTableEntries) using each drug's default model.
  6. refreshDataHandler() calls refreshData() which runs processTCI() for each dose table, stores the result in tciMap, then posts the inputs to API/Logs/SaveGraphLog.
  7. In EHR mode a timer repeats the pull every 300,000 ms (5 minutes).

EHR administration → dose event mapping

createDoseTableEntries() maps the EHR Action of each administration:

EHR ActionDose-table event
New Bag, Infusion Continued, RestartedStart Infusion if none is running, otherwise Dose Change
contains ChangeDose Change
StoppedStop Infusion
Bolus, GivenBolus (run time fixed at 10 seconds)

If an infusion is still running when anesthesia ends, a closing Stop Infusion row is added at the anesthesia end time. These action names are those of the EHR the code was written against; other EHRs may need changes in med-helpers.tsx.

Build and deploy

npm ci
npm run build

On IIS, copy .next, public, package.json, package-lock.json, next.config.ts and server.js to the site folder, run npm ci --omit=dev there, and use api/deploy/web.config.example as the site web.config (it routes /REST to the API and everything else to server.js). server.js forces NODE_ENV=production, creates a plain HTTP server around the Next.js request handler and listens on PORT, which iisnode supplies as a named pipe.
