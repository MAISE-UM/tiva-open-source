TIVA — EHR Launch Flow

What happens when TIVA is launched from an EHR with SMART on FHIR (tested with Epic): launch → authorize → callback → /auth/ehrloading → complete → /auth/ehrlaunch → dashboard FHIR data pull.

This page explains the code. The setup guide (EHR registration, key pair, every Ehr:* setting, patient data endpoints, troubleshooting) is ehr-setup.html. Route paths below are the defaults of Ehr:Routes and Ehr:ClientRoutes in api/deploy/appsettings.example.json; a site can change them.

Sequence

Browser hops are redirects or page navigations. Step 6 is a direct server-to-server call from the API to the EHR. The EHR never talks to the Next.js client, and the browser never sees the EHR tokens.

Step by step

#WhereWhat
1EhrOAuthController.LaunchThe EHR opens /REST/ehr/launch with iss, launch and the case parameters named in Ehr:LaunchParameters (case ID, reporter first and last name). The API rejects issuers not in Ehr:AllowedIssuers (an empty list accepts all and logs a warning at start-up), reads the FHIR metadata at {iss}/metadata to find the authorize URL, saves caseId|first|last under a new random state, and redirects to the EHR authorize URL with response_type=code, redirect_uri=Ehr:RedirectUrl, client_id, scope=Ehr:LaunchScope, launch, aud=iss and state.
2EHRAuthorizes the launch and redirects to Ehr:RedirectUrl with code and state.
3EhrOAuthController.CallbackStores the code in the HttpOnly cookie X-Identifier and the state in X-Ehr-State, then redirects to {JwtAuthentication:ValidIssuer}{Ehr:ClientRoutes:Loading}. ValidIssuer is therefore also the public site base URL and should end with /.
4client/app/auth/ehrloading/page.tsxFetches ehr/client-config to learn CompletePath and sends the browser to {NEXT_PUBLIC_EXTERNAL_API_BASE_URL}/{CompletePath}, which completes the login on the API.
5EhrOAuthController.CompleteExchanges the code at the token endpoint (SmartOnFhirService.ExchangeCode), authenticating with a JWT signed by Ehr:ClientAssertion:PrivateKey. Validates the id_token. Looks up the state to recover the case ID and reporter name. Resolves the TIVA user with ResolveUser: take Ehr:User:ClaimType, strip one configured prefix, optionally lower-case, look the user up (then try each FallbackSuffixes), and create the user with DefaultRoleId when AutoCreate is on. Failures redirect to Ehr:ClientRoutes:Failure.
6EhrOAuthController.SignInBuilds the TIVA access and refresh JWTs, stores a Session (EHR id/access/refresh tokens, TIVA tokens, token time, surgical log ID) in the in-memory session cache, sets X-Access-Token and X-Refresh-Token (HttpOnly) and X-Username, and deletes the temporary X-Identifier and X-Ehr-State cookies. Cookies use Secure, SameSite=None and AppSettings:COOKIE_DOMAIN.
7Complete (end)Logs the login (api.Log_Login → api.UserLogin_Log, including patient ID, MRN and reporter name), sets the readable cookie X-SurgicalID (<case id>||<patient id> for the client), and redirects to Ehr:ClientRoutes:Launched.
8client/app/auth/ehrlaunch/page.tsxNavigates to /?fromEhr=true.

Standalone launch

GET /REST/ehr/standalone sends a user to the EHR authorize page without a patient context (Ehr:StandaloneScope); /REST/ehr/standalone/callback exchanges the code, validates the id_token, resolves the user with Ehr:StandaloneUser (auto-create is off in the example) and redirects to Ehr:ClientRoutes:StandaloneLaunched. The redirect URI defaults to {ValidIssuer}REST/{Routes:StandaloneCallback} unless Ehr:StandaloneRedirectUrl is set.

Dashboard data pull

With ?fromEhr=true the dashboard reads ehr/client-config (display name and DataMapping), then searchFHIR() (client/lib/med-helpers.tsx) splits the X-SurgicalID cookie into case ID and patient ID and calls these API endpoints:

OrderClient callAPI endpoint (api.Endpoints)Used for
1getFHIRVitalSigns ({ patient })FHIR/GetVitalSigns (GET, api/FHIR/R4/Observation)Weight and height, matched by DataMapping.WeightLabel / HeightLabel (unit kg or else lb; cm or else inches). If either is missing the pull stops with an empty result.
2getEhrSurgicalCase ({ SurgicalRecordID })FHIR/GetSurgicalCase (POST, Epic web service)Patient name, sex, date of birth (age in years, or in months under 1 year) and MRN; procedure (PAFValues[DataMapping.ProcedurePafIndex]); operating room; the anesthesia start and stop timing events (AnesthesiaStartEvent, AnesthesiaStopEvent), with the discharge time as the end when there is no stop event.
3getFHIRMedicationStatements ({ patient, effective })FHIR/GetMedicationStatements (GET, api/FHIR/STU3/MedicationStatement)The patient's medication orders from 3 days before anesthesia start. An order is kept when its name matches a TIVA medication: Medication_Search_Terms is a comma-separated list; every term must appear in the name (case-insensitive), and a term starting with ! must not appear.
4getMedicationAdministrations ({ PatientID: MRN, ContactID: visit contact number, OrderIDs: ids joined by | })FHIR/GetMedicationAdministration (POST, Epic web service)Administrations for the matched orders, kept only between anesthesia start and end, sorted by time, and merged per TIVA medication.

These are rows in the database, not code. Each uses Credential_Source = UserSession and Credential_Key = FhirAccessToken: before the call the API refreshes the EHR token if it is older than Ehr:TokenRefreshMinutes (refresh-token grant with a client assertion), then sends the user's EHR access token as a bearer token to {URL base}{URL}. The browser never receives the EHR tokens. In the seed data the two Epic web-service endpoints have the placeholder URL REPLACE_WITH_EPIC_API_PATH and must be set per site. See api.html § Endpoint engine.

The dashboard repeats the pull every 5 minutes so new doses appear during the case. Administrations become dose rows with the mapping in client.html § Dashboard.

Session and hosting notes

  • Sessions (including EHR tokens), OAuth state and the endpoint cache are in process memory. Run the API as one instance; restarting it signs EHR users out and they relaunch from the EHR.
  • If Ehr:Enabled is false the EHR routes are not mapped at all.
  • GET /REST/.well-known/jwks.json publishes both the EHR client-assertion public key and the API's token-signing key (matching kids), so the EHR vendor can verify assertions and the Next.js client can verify TIVA tokens.
  • api.UserLogin_Log stores patient identifiers from the launch. Treat the database as holding protected health information.
